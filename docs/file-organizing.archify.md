# 파일 정리하기를 누르면 어떤 일이 일어날까? {#organize}

**파일 정리하기**를 누르면 설정 창이 열립니다. **분석 시작**을 누르면 앱이 정리할 폴더와 파일을 제안합니다. **이동 경로 미리보기**에서 이동을 확정하면 앱이 파일을 옮깁니다.

## ‘고유 파일과 사본 확인 중’에는 무엇을 읽나? {#identity-read}

| 조건 | 앱이 하는 일 |
| --- | --- |
| 같은 크기의 파일이 없음 | 파일을 열고 한 바이트를 읽어 접근 가능 여부를 확인합니다. |
| 같은 크기의 파일이 있음 | 각 파일 전체를 읽어서 SHA-256 값을 계산합니다. 이 값은 파일 내용을 비교하는 데 씁니다. |
| 크기와 SHA-256 값이 같음 | 대표 파일 하나를 이동 후보로 남깁니다. 나머지 사본은 원래 위치에 둡니다. |
| 오프라인이거나 읽기에 실패함 | 파일을 보류합니다. 해당 파일은 새 폴더의 최소 개수에서 제외합니다. |

앱은 이름 끝에 복사 번호가 없는 파일을 대표로 우선합니다. 조건이 같으면 경로 순서로 정합니다. 이름에 `(1)`이 있어도 내용이 다르면 고유 파일로 셉니다.[](source:identity)

## 언제 폴더가 생기나? {#folder-rule}

**새 폴더로만 정리**를 선택하면 앱이 새 폴더를 제안합니다. **기존 폴더 활용**을 선택하면 앱이 원본 위치의 하위 폴더도 목적지 후보로 살핍니다. 최소 신뢰도를 높이면 추천 기준이 엄격해집니다. 추가 분석 옵션을 켜면 일부 문서의 본문이나 표지도 확인합니다.[](source:engine)

| 예시 | 이동 결과 |
| --- | --- |
| 같은 행사 자료 3개와 내용이 같은 사본 2개 | 고유 파일 3개가 새 폴더로 이동합니다. 사본 2개는 남습니다. |
| 새 폴더 후보 3개 중 2개만 체크 | 새 폴더 생성을 보류합니다. 파일명 필터로 2개만 남겨도 같은 기준을 적용합니다. |
| 기존 폴더와 관련된 고유 파일 1개 | 해당 파일을 기존 폴더로 옮길 수 있습니다. |
| 이동 도중 오류로 새 폴더에 3개 미만만 이동 | 앱은 안전하게 되돌릴 수 있는 파일을 복원합니다. 충돌이 있으면 남은 경로와 사유를 표시합니다. |

## 파일 이름과 경로는 어디서 확인하나? {#review}

파일 정리 화면에서 화살표를 누르면 폴더가 펼쳐집니다. 여러 폴더를 함께 펼칠 수 있습니다. 파일 행에는 Windows 파일 아이콘, 파일명, 원래 폴더와 이동할 폴더가 표시됩니다. 행 끝의 정보 버튼에서 전체 경로와 추천 근거를 확인하세요.

| 파일 검색과 파일 정리에서 할 일 | 조작 |
| --- | --- |
| 항목 선택 | 이름 글자를 한 번 클릭하세요. 아이콘이나 행 여백은 선택 영역에서 제외합니다. |
| 파일이나 기존 폴더 열기 | 이름 글자를 빠르게 두 번 클릭하세요. 제안된 새 폴더에서는 파일 목록이 펼쳐지거나 접힙니다. |
| 이름 편집 시작 | 이름 글자를 한 번 클릭하세요. 잠시 뒤 같은 이름을 다시 클릭하세요. 선택한 이름에서 F2를 눌러도 됩니다. |
| 이름 저장 | 새 이름을 입력하세요. Enter를 누르세요. 실제 파일이나 기존 폴더는 디스크에서 즉시 바뀝니다. 제안된 새 폴더는 예상 경로가 바뀝니다. |
| 편집 취소 | Esc를 누르세요. |

기존 폴더의 이름을 바꾸면 그 안의 파일 경로도 바뀝니다. 앱은 남은 복원 경로를 갱신합니다. 디스크에서 바꾼 이름은 최근 정리에서 되돌릴 수 있습니다.

복원할 원래 경로에 다른 파일이 있으면 앱이 복원을 보류합니다. 이동한 파일의 내용이 바뀌거나 파일이 사라져도 복원을 보류합니다. 충돌을 해결한 뒤 같은 작업의 복원을 다시 실행하세요.

## 구현 진입점 {#source}

| 단계 | 함수 | 역할 |
| --- | --- | --- |
| 파일 수집 | `Desktop.scan()` | 선택한 원본 폴더의 바로 아래에서 파일을 수집합니다. |
| 사본 확인 | `identify_files()` | 크기별 개수를 집계합니다. 같은 크기의 파일만 전부 읽습니다. |
| 묶음 추천 | `discover_relations()` | 사본을 보류하고 이름, 시각, 위치, 출처로 관계를 계산합니다. |
| 경로 미리보기 | `Desktop.preview()` | 선택한 파일을 다시 확인합니다. 이동 계획에 일회용 토큰을 붙입니다. |
| 파일 이동 | `execute_moves()` | 이동 의도를 기록하고 목적지를 확인한 뒤 선택 파일을 옮깁니다. |
| 작업 복원 | `storage.undo()` | 복원 가능한 파일을 역순으로 원래 경로에 옮깁니다. |

## Rust로 바꾸면 얼마나 빨라질까? {#speed}

다음 값은 Windows에서 Python 3.13으로 사본 확인 단계만 측정한 결과입니다. 임시 파일 12개를 사용했습니다. 준비 실행 후 다섯 번 측정한 중앙값입니다. 운영체제의 파일 캐시는 비우지 않았습니다.

| 시험 조건 | 전체 해시를 계산한 양 | 걸린 시간 |
| --- | --- | --- |
| 파일마다 8MiB에 0~11바이트를 더해 크기를 다르게 함 | 0바이트 | 1.7ms |
| 파일 12개의 크기를 각각 8MiB로 맞춤 | 96MiB | 42.6ms |

현재 앱은 Python의 `hashlib.file_digest`로 SHA-256을 계산합니다. Python은 이 계산에 네이티브 코드를 사용합니다.[](source:hash)

디스크 읽기가 시간을 차지하면 같은 양을 읽는 Rust 구현에서도 읽기 시간이 듭니다. 수천 개 파일의 관련도 계산에서 CPU 시간이 크면 해당 계산을 Rust로 옮겨 시험할 수 있습니다. Rust의 속도 향상률은 같은 파일로 두 구현을 비교해야 알 수 있습니다.
