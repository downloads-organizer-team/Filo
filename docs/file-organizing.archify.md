# 파일 정리하기를 누르면 어떤 일이 일어날까? {#organize}

**파일 정리하기**를 누르면 설정 창이 열립니다. **분석 시작**을 누르면 앱이 정리할 폴더와 파일을 제안합니다. **파일 이동**을 누르면 선택한 파일을 옮깁니다. **이동 경로 미리보기**로 목적지를 먼저 볼 수 있습니다.

## 정리 원칙 {#principles}

형식이 달라도 같은 작업에 쓴 파일을 다시 찾을 수 있어야 합니다. 기본 분석은 파일명, 번호, 시각, 저장 위치와 다운로드 출처에서 그 관계를 찾습니다.

- 같은 작업이라는 근거가 약하면 미분류에 둡니다.
- 새 폴더는 내용이 다른 파일이 3개 이상일 때 만듭니다. 같은 내용의 사본은 한 번만 셉니다.
- 기존 폴더가 같은 작업을 담고 있으면 그곳을 먼저 추천합니다. 다른 작업은 구분해서 찾을 수 있게 합니다.
- 이동 전에는 묶은 이유와 원래 위치, 목적지를 한 화면에서 보여 줍니다. 이동 후에는 기록을 남겨 되돌릴 수 있게 합니다.

## ‘고유 파일과 사본 확인 중’에는 무엇을 읽나? {#identity-read}

| 조건 | 앱이 하는 일 |
| --- | --- |
| 같은 크기의 파일이 없음 | 파일을 열고 한 바이트를 읽어 접근 가능 여부를 확인합니다. |
| 같은 크기의 파일이 있음 | 각 파일 전체를 읽어서 SHA-256 값을 계산합니다. 이 값은 파일 내용을 비교하는 데 씁니다. |
| 크기와 SHA-256 값이 같음 | 대표 파일 하나를 이동 후보로 남깁니다. 나머지 사본은 원래 위치에 둡니다. |
| 오프라인이거나 읽기에 실패함 | 파일을 보류합니다. 해당 파일은 새 폴더의 최소 개수에서 제외합니다. |

앱은 이름 끝에 복사 번호가 없는 파일을 대표로 우선합니다. 조건이 같으면 경로 순서로 정합니다. 이름에 `(1)`이 있어도 내용이 다르면 고유 파일로 셉니다.[](source:identity)

## 언제 폴더가 생기나? {#folder-rule}

**새 폴더로만 정리**를 선택하면 앱이 새 폴더를 제안합니다. **기존 폴더 활용**을 선택하면 앱이 원본 위치의 하위 폴더도 목적지 후보로 살핍니다. 확장자별 모드는 사본 확인 뒤 마지막 확장자로 분류합니다. 관련 작업별 모드에서 최소 신뢰도를 높이면 추천 기준이 엄격해집니다. 추가 분석 옵션을 켜면 일부 문서의 본문이나 표지도 확인합니다.[](source:engine)

관련 작업별로 기존 폴더를 찾을 때는 묶음 이름, 새 파일명, 폴더명, 안에 보관된 파일명과 다운로드 출처를 대조합니다. 같은 주제라도 폴더명에 적힌 연도·학기·기수가 다르면 분리합니다. 예를 들어 ‘봄축제’ 폴더에 한 해 자료만 있으면 다음 해 자료는 별도로 검토합니다. 여러 해의 축제 자료를 함께 모아 왔다면 같은 폴더를 추천할 수 있습니다. 이동할 파일이 있는 폴더만 추천 목록에 나타납니다.

| 예시 | 이동 결과 |
| --- | --- |
| 같은 행사 자료 3개와 내용이 같은 사본 2개 | 고유 파일 3개가 새 폴더로 이동합니다. 사본 2개는 남습니다. |
| 새 폴더 후보 3개 중 2개만 체크 | 새 폴더 생성을 보류합니다. 파일명 필터로 2개만 남겨도 같은 기준을 적용합니다. |
| 기존 폴더와 관련된 고유 파일 1개 | 해당 파일을 기존 폴더로 옮길 수 있습니다. |
| 이동 도중 오류로 새 폴더에 3개 미만만 이동 | 앱은 안전하게 되돌릴 수 있는 파일을 복원합니다. 충돌이 있으면 남은 경로와 사유를 표시합니다. |

## 파일 이름과 경로는 어디서 확인하나? {#review}

폴더 행의 빈 곳이나 화살표를 누르면 하위 목록이 열립니다. 폴더 체크박스는 표시된 하위 파일을 함께 선택하거나 해제합니다. 여러 폴더를 함께 펼칠 수 있습니다. 파일 행에는 Windows 파일 아이콘, 파일명, 원래 폴더와 이동할 폴더가 표시됩니다. 행 끝의 정보 버튼에서 전체 경로와 추천 근거를 확인하세요.

| 파일 검색과 파일 정리에서 할 일 | 조작 |
| --- | --- |
| 항목 선택 | 이름 글자를 한 번 클릭하세요. 아이콘이나 행 여백은 선택 영역에서 제외합니다. |
| 파일이나 기존 폴더 열기 | 이름 글자를 빠르게 두 번 클릭하세요. 제안된 새 폴더에서는 파일 목록이 펼쳐지거나 접힙니다. |
| 이름 편집 시작 | 이름 글자를 한 번 클릭하세요. 잠시 뒤 같은 이름을 다시 클릭하세요. 선택한 이름에서 F2를 눌러도 됩니다. |
| 이름 저장 | 새 이름을 입력하세요. Enter를 누르세요. 실제 파일이나 기존 폴더는 디스크에서 즉시 바뀝니다. 제안된 새 폴더는 예상 경로가 바뀝니다. |
| 편집 취소 | Esc를 누르세요. |

기존 폴더의 이름을 바꾸면 그 안의 파일 경로도 바뀝니다. 앱은 남은 복원 경로를 갱신합니다. 디스크에서 바꾼 이름은 최근 정리에서 되돌릴 수 있습니다.

복원할 원래 경로에 다른 파일이 있으면 앱이 복원을 보류합니다. 이동한 파일의 내용이 바뀌거나 파일이 사라져도 복원을 보류합니다. 충돌을 해결한 뒤 같은 작업의 복원을 다시 실행하세요.

파일 검색은 Everything 색인에서 이름을 찾아 최대 200개 경로를 표시합니다. 파일 정리는 선택한 원본 폴더 바로 아래만 수집합니다. 여러 원본을 합쳐 분석 대상이 3,000개를 넘으면 분석을 중단합니다.

## 구현 진입점 {#source}

| 사본 확인 | `identify_files()` | 크기별 개수를 집계합니다. 같은 크기의 파일만 전부 읽습니다. |
| 관련 작업별 | `discover_relations()` | 사본을 보류하고 이름, 시각, 위치, 출처로 관계를 계산합니다. |
| 확장자별 | `extension_study()` | 사본과 확장자가 없는 파일을 제외하고 마지막 확장자로 묶습니다. |
| 기존 폴더 활용 | `folder_score()` | 후보 폴더마다 바로 아래 항목을 최대 100개 살피고, 파일 최대 12개의 다운로드 출처를 확인합니다. 한 묶음의 파일들이 같은 목적지를 지지하고 차점 후보와 점수 차이가 충분할 때 추천합니다. |
| 경로 미리보기 | `Desktop.preview()` | 선택한 파일을 다시 확인합니다. 이동 계획에 일회용 토큰을 붙입니다. |
| 파일 이동 | `execute_moves()` | 이동 의도를 기록하고 목적지를 확인한 뒤 선택 파일을 옮깁니다. |
| 작업 복원 | `storage.undo()` | 복원 가능한 파일을 역순으로 원래 경로에 옮깁니다. |

## 실제 다운로드 폴더의 병목과 Rust 전환 {#speed}

다운로드 폴더의 파일 1,813개를 분석했습니다. 첫 측정에서는 사본 확인이 가장 오래 걸렸습니다. 직후 반복에서는 유사도 행렬과 정밀 분석이 전체 분석 시간의 약 71%를 차지했습니다.

2026-11-26 · Windows x64 · Python 3.13 · 커밋 1fef343. 같은 프로세스에서 같은 폴더로 Desktop.scan()과 Desktop.preview()를 두 번 실행했습니다. 파일 캐시는 통제하지 않았습니다. 새 폴더 모드, 최소 신뢰도 0.7, 본문·표지 분석을 사용했습니다. 두 실행 모두 묶음 88개, 이동 후보 467개가 나왔습니다. 추천 정확도는 평가하지 않았습니다.

| 단계 | 첫 측정 (초) | 직후 반복 (초) |
| --- | --- | --- |
| 분석 전체 | 59.44 | 14.12 |
| 파일 수집 | 0.15 | 0.07 |
| 고유 파일·사본 확인 | 38.88 | 1.32 |
| ↳ 그중 전체 해시 호출 | 6.25 | 1.20 |
| 파일명·메타데이터 추출 | 6.93 | 0.21 |
| 유사도 행렬 계산 | 3.94 | 4.18 |
| 계층 군집화 | 0.76 | 0.73 |
| 중간 신뢰도 후보 정밀 분석 | 7.04 | 5.90 |
| 이동 미리보기 (분석 후 별도) | 2.81 | 1.67 |

**첫 실행에서 무엇을 기다렸나**　크기가 겹친 295개 파일에서 약 2.95 GiB를 전체 해시했습니다. 사본 확인의 경과 시간은 38.88초, 프로세스 CPU 시간은 1.61초였습니다. 전체 해시 호출 밖에서 약 32.64초가 흘렀습니다. 첫 실행에서는 파일 상태 조회·열기·첫 읽기 시간을 따로 재지 않아 대기 원인을 특정할 수 없습니다.

**Rust를 시험할 구간**　직후 반복에서 유사도 행렬은 경과 4.18초에 CPU 4.02초, 정밀 분석은 경과 5.90초에 CPU 5.69초였습니다. 파일마다 호출하는 방식보다 특징 데이터를 한 번 전달해 행렬 전체를 계산하는 Rust 시제품을 먼저 비교할 수 있습니다. 같은 입력에서 점수·묶음·미분류 결과도 대조해야 합니다.

**속도 추정의 한계**　두 구간의 경과 시간이 모두 절반으로 줄고 나머지 비용이 같다고 가정하면 재분석은 약 14.1초에서 9.1초가 됩니다. Rust 구현의 실측값은 없습니다. 미리보기 467개까지 측정했으며, 이동 확정 시 execute_moves()가 원본을 다시 해시합니다. 창 렌더링·실제 이동·복원 시간은 측정 범위 밖입니다.

**개선 제안 · 사용자 경험**　사본 확인 중에는 처리한 파일 수와 해시한 바이트 수를 표시하고 대용량 파일을 읽는 중에도 취소를 반영하는 방안을 검토합니다. 현재 화면 하단에는 선택한 폴더 수와 파일 수를 표시합니다. 보류·충돌 항목을 한곳에서 검토하는 기능은 후속 개선 대상입니다.

**개선 제안 · 개발 우선순위**　다음 첫 실행에서 상태 조회·열기·첫 읽기·전체 해시·닫기를 나눠 계측합니다. 정밀 분석에서는 문서 처리와 점수 재계산을 분리합니다. 파일명과 경로 없이 구간별 시간·개수·바이트만 기록하면 입력 규모가 다른 폴더끼리 비교할 수 있습니다.

**임시 파일 대조 실험**　사본 판정만 분리한 보조 실험입니다. 서로 다른 내용의 임시 파일 12개를 사용해 준비 실행 후 5회의 중앙값을 구했습니다. 파일마다 8 MiB에 0~11바이트를 더한 조건은 전체 해시 입력 0바이트에 1.7ms, 모두 8 MiB인 조건은 96 MiB에 42.6ms였습니다.

## 분류 방식별 실제 폴더 검증 {#grouping}

새 폴더로만 정리에서 각 조건을 한 번씩 실행했습니다. 관련 작업별 최소 신뢰도는 0.5입니다. 두 번째로 실행한 확장자별 시간에는 디스크 캐시의 영향이 있을 수 있습니다.

| 다운로드 | 1,813 | 확장자별 | 31 | 1,603 | 4.1초 |

실제 폴더에서는 추천까지 확인했습니다. 이동과 복원은 임시 폴더로 검증했습니다. 전체 추천의 정확도를 계산하려면 사람이 정한 정답 묶음이 필요합니다.
